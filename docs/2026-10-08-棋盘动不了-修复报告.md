# 「最强引擎设置下棋盘根本动不了」修复报告（2026-10-08）

> 用户报的两件事：① 满配后跑基准只有 **387%**（≈4 核），② 最强引擎设置下**棋盘根本动不了**。
> 本报告记录**复现 → 根因 → 改动 → 验证**的全过程，所有结论都有可复现命令与前后证据。
> 同一天后续追加了两轮：**满配降到 12 线程 + 修复既有问题**（见第六节）、
> **界面高级感改造「墨玉金」主题 + 菜单栏黑条修复**（见第八节）。

## 零、界面改造（第八节详述）速览

- **菜单栏黑条的根因**：Fyne 的菜单栏用 `theme.ColorNameBackground` 当自己的底色
  （`internal/driver/glfw/menu_bar.go:40`），而本项目把它映射成**全透明**（本意是让自绘背景层透出来）
  → 菜单栏画在窗口的黑色清屏色上。修法：给这个颜色一个不透明值（内容区背景由自绘图层负责）。
- **新增皮肤「墨玉金」**：深墨底 + 单一暖金强调色 + 层次卡片 + 压暗胡桃木棋盘（程序生成木纹）
  + 象牙白棋子带高光 + 深色系统标题栏。**设置 → 主题** 里一键切换，`config.json` 的 `theme` 字段记住。
- **背景照片换成主题底纹**：程序生成的微颗粒 + 一角柔光 + 四周压暗，任意分辨率都清晰，
  且跟着皮肤走。想用回照片把 `background_style` 设成 `"image"` 即可。

## 一、结论先说

| # | 缺陷 | 根因 | 证据 |
|---|---|---|---|
| 1 | 满配 387%（线程 15 从未生效） | `ToggleMaxStrength` 只改配置值，而 Threads/Hash/MultiPV **只在引擎启动时**读 setoption | 复现：开满配后引擎仍是 4 线程；修后基准 **1318%** |
| 2 | 进程调优与实测不符 | 调优作用在**旧进程**上，引擎一重启就丢；且用的是 HIGH 而不是 ABOVE_NORMAL | 实测引擎 `Normal/0xFFFF`，状态栏却说"已绑 15 个核"；修后 `AboveNormal/0xFFFE` |
| 3 | 人机对弈**永久锁盘**（引擎空转） | 命中局面缓存的分支只回放结果、**不交招** | 复现：同一局面第二次走到 → `moves=1` 卡死、`analyzing=false`、引擎 CPU 不再增长 |
| 4 | 无限分析带进人机对弈会锁盘 | 无限 = 引擎不收 stop 不回 bestmove → 永远不交招 | 现已在人机对弈降级为每步限时；分析模式仍真无限（跑过 65 秒仍在算） |
| 5 | 无限分析"存不住"（选了自己变回去） | ① `SaveConfig` 每 20 秒把 TimeMode 重写成 movetime/depth；② 每个模式自己的思考设置不认 infinite；③ `HardTimeout` 把无限当成"固定深度 1 层"→ 63 秒强行 stop | 修复前：配置写 infinite，启动 1 秒后诊断行已是 movetime |
| 6 | **随机崩溃**（启动即死） | `go a.startKibitzer()` 里跨线程改 UI（`KibitzerPanel.SetIdle`），Fyne 的文本整形器是进程内唯一、内部复用一个 buffer，主线程排版与后台协程并发整形把游标写坏 → `index out of range` | `go build -race` 抓到 73 条竞争，两侧栈直接点名 `panels.go:547`；修复前 7 次启动崩 3 次，修复后 8/8 正常、race **0 条** |
| 7 | 点不动却不说为什么 | 棋盘不可交互时静默吞掉点击（对战模式/看历史局面） | 现在状态栏直接说明原因（见 `boardBlockedReason`） |

* `XQ_CONFIG=<path>`：把 config.json 重定向到独立文件 —— 验证**不会碰用户的** `config.json`（本轮验证前后哈希一致）。
* `XQ_DIAG=1`：每秒一行状态机快照（模式 / 轮到谁 / 棋盘可否点 / 是否在算 / 着数 / 引擎进程与 CPU / 关键配置）。"棋盘动不了"这类问题从窗口外面看不出来，靠这一行定位。

## 三、关键前后数据

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 10 秒基准实测 CPU 占用 | **387%**（≈3.9 核） | **1318%**（≈13.2 核 / 共 16） |
| 基准 nps / 深度 | 4,221,855 / 27 层 | 9,054,541 / 30 层 |
| 满配开关后的引擎进程 | 仍是旧线程数（4 线程 / 512MB） | **新进程** 15 搜索线程 / 4GB 哈希 |
| 引擎进程优先级 / 亲和性 | `Normal` / 全 16 核（状态栏却说已绑核） | `AboveNormal` / `0xFFF0`（12 线程用 4~15 号核，留 4 核给界面） |
| 满配线程数 | 15（= 逻辑核−1），实测 1318% | **12**（留 4 核），实测 **1185% / 名义 1200% = 98.8%** |
| 同一局面第二次走到（人机对弈） | 永久卡死（引擎空转、棋盘点不动） | 1 秒内从缓存交招，棋盘恢复可点 |
| 无限分析 | 存不住；人机对弈会锁盘；63 秒被强停 | 持久生效；人机对弈自动降级；分析模式真无限（65 秒仍在算） |
| 「手动摆盘」进出一次 | 人机对弈里棋盘**永久点不动**（交互条件漏了人机分支） | 退出摆盘即恢复可点 |
| 引擎正忙时点基准 | 必然失败（`引擎正忙（上一次思考尚未结束）`） | 先停掉在跑的思考再跑，成功出结果 |
| 引擎重启重叠 | 各起一个进程，先起的变野进程（占 CPU 到退出） | 串行化，不再产生野进程 |
| 启动崩溃 | 7 次里 3 次 panic（首屏排版） | 8 次 0 panic；`-race` 报告 73 → 0 |
| 后台改界面的写入顺序 | 菜单体检 `-race` 报 3 条 DATA RACE（状态栏文字） | 改用 `DoAndWait`（`uiDoWait`）后 **0 条** |
| 回归保障 | — | `gofmt` 干净、`go vet` 0、`go test -race ./...` 全绿、菜单体检 41 项 0 panic、对战 2 局打完 |

## 四、改动清单

**功能缺陷**
* `ui/menu.go`：满配开关（开/关）都**重启分析引擎**把参数真正下发；思考设置里「无限分析（仅分析模式）」，并说明人机对弈为何降级。
* `ui/menu.go`：满配线程数改为 `MaxStrengthThreads(逻辑核)` = 每 4 核留 1 个、上限 12（16 核 → 12 线程）；启动时把配置里旧的「逻辑核−1」自动迁移到新值。
* `ui/bench.go`：新增 `applyMaxStrengthToEngine`（重启→等新进程→调优，顺序不能反）与 `waitEnginePID`；新增 `stopAnalysisForBench`（基准前先停掉在跑的思考，否则必然报"引擎正忙"）。
* `ui/proc_windows.go`：优先级改用 **ABOVE_NORMAL**（原来用 HIGH 却对外说"高于正常"；HIGH 在多线程满载时会饿死界面）；亲和性掩码按**实际线程数**留核（12 线程 → 0xFFF0）。
* `ui/bridge.go`：缓存回放**也要交招**；人机对弈里无限分析降级为每步限时（最少 1 秒）；每次引擎重启后补做进程调优；`kibSetIdle` 把参考引擎卡的更新放回主线程；`restartAnalysisEngine` 加锁串行化；`toggleEditMode` 不再自己拼交互条件（人机对弈进出摆盘后棋盘会永久点不动）。
* `ui/bridge.go` `onParamsChanged`：引擎设置面板不再把「无限分析」顺手改成每步限时。
* `ui/human.go` + `ui/board.go`：棋盘点不动时说明**为什么**（对战模式只展示 / 正在看历史局面 / 轮到电脑）。
* `ui/app.go`：`SaveConfig` 不再把「无限分析」重写成 movetime/depth；看门狗字段；新增 `uiDoWait`（后台改界面用 `DoAndWait`，写入顺序确定，`-race` 从 3 条报告降到 0）。
* `engine/protocol.go`：`Limit.HardTimeout()` 显式处理无限分析（原来掉进"固定深度 1 层"分支，63 秒强停）。
* `config/config.go`：每个模式自己的思考设置接受 `infinite`。

**兜底（防同类问题复发）**
* `ui/bridge.go` `humanTurnWatchdog`：人机对弈里「轮到电脑、引擎活着、却没有任何搜索在途」连续 3 秒成立就自动补发请求，最多 5 次后给出可操作提示 —— 把"永久锁死"降级成"最多多等 3 秒"。

**测试与验证台**
* 新增回归测试：`ui/fix_regression_test.go`、`engine/limits_hardtimeout_test.go`、`config/think_profile_test.go`（7 条，全部针对本轮修掉的缺陷）。
* 新增验证台：`tools/xqcase.ps1`（含引擎进程线程数/优先级/亲和性采样）、`tools/xqrealmove.ps1`（真鼠标走子）、`tools/mkcfg.py`（生成独立配置）。
* `ui/verify_hooks.go`：新增 `XQ_CONFIG` / `XQ_DIAG` / `XQ_MOVES2` / `XQ_MAXSTRENGTH` / `XQ_BENCH`（仅设置环境变量时生效，正常双击运行一个都不触发）。

| 问题 | 现象 | 根因 | 修法 |
|---|---|---|---|

| 后台改界面的写入顺序不确定 | `-race` 在菜单体检里报 3 条 DATA RACE（状态栏文字） | 用的是 `fyne.Do`（Fyne 2.8 里它是**不等**的） | 新增 `uiDoWait`（`DoAndWait`）用于后台改界面，`-race` 3 → 0 |

## 八、界面高级感改造（2026-10-08 第三轮）

### 8.1 菜单栏黑条（缺陷）

| 项 | 内容 |
|---|---|
| 现象 | 菜单栏「引擎 局面 对局 棋谱 设置 帮助」那一条是黑的，文字灰暗难认 |
| 根因 | Fyne 的菜单栏把 `theme.ColorNameBackground` 当自己的底色（`menu_bar.go:40/161`）；本项目为让自绘背景层透出来，把这个名字映射成 **A=0x00 全透明** → 菜单栏画在窗口的黑色清屏色上 |
| 修法 | 该色改为**不透明**（内容区背景由 App 自绘的底纹/图片层负责，不受影响）。同一处还顺手修掉了"引擎管理窗口/弹窗底色发黑"的隐患 |
| 验证 | `_verify\shot-classic.png`（浅色皮肤下菜单栏是米黄）、`theme_test.go` 断言该色 alpha≠0 |

### 8.2 新增皮肤「墨玉金」（设置 → 主题 可一键切换）

设计依据来自本轮联网查到的三条：[Material 3 颜色角色](https://m3.material.io/styles/color/roles)
（层次靠 surface 明度差、单一强调色、outline 只做分隔）、
[UI 排版 10 条规则](https://medium.com/@atnoforuiuxdesigning/typography-in-ui-design-10-rules-that-will-instantly-improve-your-interfaces-60604c8cb825)
与 [Figma UI 原则](https://www.figma.com/resource-library/ui-design-principles)（克制：字号只留 3 档、次要信息降对比度）。

| 维度 | 做法 |
|---|---|
| 配色分层 | 窗口 `#14161A` → 面板 `#1B1E25` → 卡片 `#21252D` → 选中 `#3D3522`，全部同一冷墨色相；**只用金色 `#C9A961` 一个强调色** |
| 卡片 | 去掉硬描边，改层次底色 + 圆角 10 + 轻投影（elevation 思路）；浅色皮肤仍保留细描边 |
| 棋盘 | 压暗胡桃木 `#30281E` + **程序生成木纹**（强度 9：16 会看出条纹、5 以下看不出木头）+ 金色外框 + 象牙白棋子带左上高光 |
| 背景 | 换成**程序生成底纹**：微颗粒（确定性哈希，零均值起伏）+ 左上柔光 + 四周压暗；任意 DPI 都清晰 |
| 系统标题栏 | 深色皮肤时调 `DwmSetWindowAttribute(DWMWA_USE_IMMERSIVE_DARK_MODE)` 把标题栏也变深（本机实测"设置成功"；老系统会静默保持默认） |

### 8.3 换肤是**整体**的（新代码结构）

- `ThemeProvider` 现在给出一整套 `palette`（含棋盘皮肤 + 背景底纹参数），
  `SetActiveTheme()` 把颜色写回包级变量 → 几百处取色点无需改动就能整体换色；
- `applyThemeName()` 一次完成：调色板 → Fyne 主题 → 背景层 → 棋盘皮肤 → 标题栏；
- 换肤只能通过 `SetActiveTheme`（不许散着改颜色），这条由 `TestSetActiveThemeSwapsEverything` 守着
  —— 它当场抓到了"`classicPalette()` 引用了包级变量，导致切回经典会再涂一遍墨金"的 bug。
