> **为什么中文提示文案放在 `tools\msg-*.txt`、批处理本身是纯 ASCII？**
> 实测发现 cmd.exe 解析「含多字节汉字的批处理文件」不可靠：会丢字节偏移，把半行中文当命令执行
> （报 `'。启动失败时窗口会停住…' 不是内部或外部命令`）。UTF-8（带/不带 BOM）、GBK、中文文件名、
> ASCII 文件名各种组合都复现过；同一份内容改成「ASCII 批处理 + `type` 输出 UTF-8 文本」后 100% 正常。
> 因此所有 `.bat`/`.cmd` 只保留纯 ASCII 逻辑，中文用 `type tools\msg-*.txt`（逐字节输出，
> 不经过批处理解析器）显示，并先 `chcp 65001` 保证 UTF-8 正常渲染。

### ⚠ 重要更正：R1 / R2 未复现，属测试方工具造成的假阳性

任务书要求「真实根因与推测不同时按真实根因修复，并在交付说明里指出差异」。如实说明：

1. **测试方的截图工具抓错了画面。** 软件窗口是 GLFW30 + OpenGL。测试方用的是 DPI 不感知的 GDI 截图
   （客户区 1844×1016 物理被按 1475×812 抓取），抓到的是**被裁掉右下角**的画面 —— 于是看起来
   「红方底线只露一半、底部操作栏整排看不到」。**同一批证据里，测试方自己用整尺寸抓的另一张图
   `screenshots/10-bridge-analysis.png`（1844×1016）完整显示了棋盘全部 10 行与两行底部操作栏**，两者互相矛盾。
2. **本轮用任务书规定的 `PrintWindow(hwnd, hdc, 2)` 真窗口截图复现：默认窗口下棋盘 10 行完整、
   底部两行操作栏与状态栏全部可见**（见 `_verify/v131-01-default.png`）。
3. **点击错位同样是工具造成的。** 用 DPI 感知的取证工具（先 `SetThreadDpiAwarenessContext(PER_MONITOR_AWARE_V2)`）
   真实点击 b9 黑马，应用日志给出 `[hit] ev.Position=(72.8,90.0) … -> sq=82 ok=true`，
   sq=82 正是 b9，界面随即显示 a7/c7 两个合法落点 —— **命中完全准确**。测试方用 DPI 不感知的
   PowerShell 计算屏幕坐标，会被系统按 1.25 缩放，从而产生系统性偏移。
4. **本轮确实发现并修掉了三个真问题**（与测试方描述的现象不同，但属于同一类隐患）：
   - Fyne 的 content scale 在本机是 **1.3**（按显示器**物理** DPI 156 / 基线 120 计算，与 Windows 的 125% 无关），
     「逻辑尺寸 × scale」这条链路必须显式同源；已改为棋盘几何由逻辑尺寸派生、再按实际缩放因子放大。
   - `clampWindow` 缺「窗口小于内容所需」的纠正。
   - **本版新增 R5 界面时踩到的新坑**：`canvas.Text.MinSize()` 会把带 `\n` 的整段文本当成**一整行**量宽，
     一段 110 字的警告报出约 1200 逻辑像素的最小宽度，Fyne 随即把窗口撑到 **2371 物理像素**（远超 1920 屏幕）。
     已改成「每行一个 `canvas.Text`」，`matchRoot` 最小宽度从 1203 降到 402。

- `gofmt -l` 全树干净（修掉 6 个历史遗留未格式化文件）

### D. 已知限制（如实列出，未修）

- 回放/跳转历史局面时，引擎不会重新分析未算过的局面（**这是用户明确要求的行为**：只用缓存），此时面板显示「该局面还没有分析结果」。

- 分栏手柄已加宽到 14 逻辑像素且可见，但脚本化拖拽仍推不动（合成鼠标事件），需人工确认真机手感。
- `XQ_*` 验证钩子编译在正式产物里（只在设置对应环境变量时生效），便于复现问题，未做构建标签隔离。

## 一、产品定位

本软件面向两个真实场景：

| 场景 | 你在做什么 | 本软件在做什么 |
| --- | --- | --- |
| **A. 引擎桥接分析（核心）** | 你在手机/电脑上的第三方象棋软件里对弈，同时打开本软件当「最强棋手」 | 你把第三方软件的最新着法摆到本软件棋盘上，内置 Pikafish 满配引擎立即深度思考，给出最强应对；你一键复制 UCI 坐标，粘贴回第三方软件走棋 |
| **B. 引擎自动对战** | 你想实测两个引擎的相对实力 | 本软件加载两个引擎（己方 + 对手）批量自动对弈 N 局，统计胜/和/负、深度、节点，保存棋谱与报告 |

**明确不做**（本版不含任何相关代码）：人机对弈游戏、AI 模型评语、复盘数据库、杀法/残局训练营、联机对战、云同步。

## 二、运行方式

### 最简方式（推荐）

双击 `start.bat`，或直接双击 `xiangqi.exe`。

`start.bat` 会先找 `xiangqi.exe`：存在就直接启动；不存在才尝试用本机 Go 工具链现场编译（并给出缺 Go / 缺 GCC 的明确提示）。

### 首次运行会自动生成

| 文件 | 说明 |
| --- | --- |
| `config.json` | 全部可调参数与界面状态；不存在则按默认值创建 |
| `engines.json` | 引擎注册表；不存在则自动注册预置皮卡鱼目录 |
| `engines\` | 引擎库目录（可放任意多个引擎子目录） |
| `matches\` | 自动对战产出目录（棋谱 `game_00N.pgn`、`all_games.pgn`、`report.txt`） |

### 前提

- 已放置 `assets\background.jpg`（可选；没有则回退护眼纯色底并在状态栏提示）
- 引擎库中至少有一个引擎。首次运行会自动把本机预置目录
  `C:\Users\ASUS\Doubao\chats\2026-10-04\new-chat\皮卡鱼 20260906\`
  里的 Pikafish 注册为默认己方引擎。

2. **同一个动作不留两个按钮**（复制最佳着法、棋盘大小各留一处）；
3. **点菜单就直接开始**：点工具栏「引擎对战」或菜单「对局 → 开始对战」立刻开赛；
4. **能自动就不放按钮**：粘贴棋谱后自动重放并分析（原「应用着法序列」按钮已删）；
5. **术语与格式一律照同类软件**（TCHESS / 象棋巫师 / swiftxiangqi，含统计行字段顺序等细节）。

- 主横向分栏（棋盘区 ｜ 分析区）与右侧纵向分栏**都可拖动**，分栏位置自动记忆到 `config.json`。
- 默认左栏占 62%（棋盘更宽、右栏更窄）；菜单「设置 → 棋盘：大 / 中 / 小」可改。
- 窗口缩放时棋盘按 9:10 比例自适应，最小尺寸下限 380×420 保证可操作。

## 四、核心功能 A：引擎桥接分析

### 4.1 三种局面输入方式（传棋手的三种姿势）

| 方式 | 操作位置 | 说明 |
| --- | --- | --- |
| **a. 点击走子** | 棋盘 | 点选己方棋子 → 高亮显示全部合法落点 → 点目标格落子。非法着法（含自将、将帅照面）立刻弹提示，不会走上去 |
| **b. 坐标输入框** | 左下角输入框 | 输入 `h2e2 h9g7 c3c4` 回车，**从头按初始局面重放全部着法**，保证局面与第三方软件一致。棋盘每走一步也会自动回填这个框 |
| **c. 手动摆盘** | 「手动摆盘」按钮 | 支持任意局面编辑：选棋子 → 点交叉点放置；「橡皮」移除；「清空棋盘」清空；「初始局面」复位。用于第三方软件的非标准局面 |

### 4.2 输入即思考

局面一变（走子、悔棋、粘贴、摆盘、改参数）**自动**发起 `go`，不需要点「开始」。
思考中状态栏实时显示当前深度、节点数、耗时与红方胜率预览；曲线区同时显示一个空心预览点。

### 4.3 分析面板

- **最佳着法区**：中文记谱（如「炮二平五」）+ UCI 坐标 + 红方胜率 + 主变例前 5 步 + 深度/节点/速度/耗时。
- **多候选列表**：MultiPV 开 K 条（K 默认 8，滑块 1~12）。每条显示中文记谱、UCI、概率百分比、引擎分值、进度条，底部显示 **概率合计（恒为 100%）**。
- **局势曲线**：Canvas 自绘红黑双线，X = 步数，Y = 胜率 0~100%（红线 = 红方胜率，黑线 = 黑方胜率）。每分析完一个局面记录一点，重开清空，思考中含预览点。
- **着法列表**：每步显示序号、走子方、中文记谱、UCI 坐标；点击任意一步可跳转查看该步之后的局面（查看中棋盘锁定，点「回到当前局面」恢复）。

### 4.4 一键复制最佳着法（核心按钮）

点「复制最佳着法」→ 剪贴板内容为 **4 字符 UCI 坐标**（如 `h2e2`）→ 底部 toast 提示 `已复制：炮二平五（h2e2）`。直接粘贴回第三方软件即可。

### 4.5 粘贴输入区

「粘贴输入」页是多行文本框：把第三方软件的整个着法序列粘进来，点「应用着法序列并立即分析」。
兼容多种格式：

```
h2e2 h9g7 c3c4
1. h2e2 h9g7 2. c3c4
position startpos moves h2e2 h9g7
h2e2,h9g7，c3c4、i0i1        ← 换行 / 逗号 / 顿号 / 分号 / 竖线均可
```

无法识别的记号会被跳过并在状态栏提示，不会中断已能识别的部分。

### 4.6 悔棋 / 撤销

「悔棋一步」「撤销全部」。本模式没有对弈胜负概念，撤销就是回退着法；曲线会同步回退到当前着数。

## 五、核心功能 B：引擎自动对战

### 5.1 配置

- **己方引擎 / 对手引擎**：都从引擎库下拉选择；对手引擎也可以先「引擎管理 → 添加外部引擎目录」再选。最近选择持久化到 `config.json`。
- **对局数 N**：滑块 1~100，默认 10。
- **时间控制（三选一）**：每步限时（movetime 毫秒）／每局总时间（按每方约 60 步均摊，下限 200ms）／固定深度。
- **先后手轮换**：勾选后奇数局己方执红、偶数局执黑。
- **开局库**：引擎若上报 `OwnBook` / `BookFile` 之类参数，会出现在参数面板的「引擎动态参数」里，可直接设置；引擎不支持则不显示。

### 5.2 对弈流程与健壮性

- 两个引擎各自独立子进程 + 独立读取 goroutine，**串行交替**走子（A 走完 B 走），UI 永不阻塞。
- 每步都由本软件的规则引擎（`rules` 包）校验合法性，非法直接判负并记录原因。
- 判负/判和规则：

| 情况 | 判定 |
| --- | --- |
| `bestmove` 坐标非法 / 不符合中国象棋规则 | 该方判负 |
| `bestmove` 为 `none` / `0000` / 空 | 该方判负 |
| 引擎思考超时或进程崩溃 | 该方判负（另一引擎不受影响） |
| 无合法着法且被将军 | 将死，走子方负 |
| 无合法着法且未被将军 | 困毙，中国象棋规则同样判走子方负 |
| 同一局面出现 3 次 | 判和（覆盖长将循环） |
| 达到 400 着上限 | 判和（**保证绝不无限循环**） |

### 5.3 实时显示

当前局数/总局数、比分（己方 胜-和-负）、当前棋盘同步展示、双方胜率曲线、对局日志（何时开始、何时结束、判负原因、棋谱文件名）。

## 六、引擎库与追加引擎

### 6.1 目录约定

- 默认引擎库：`engines\`（与 exe 同目录），支持子目录，**每个引擎放一个子目录**。
- 也支持「添加外部引擎目录」：任意文件夹（例如已预置的皮卡鱼目录），路径记入 `engines.json` 的 `search_dirs`。

### 6.2 自动发现

启动时与点「重新扫描引擎」时，扫描引擎库全部子目录（深度 3 层），对每个 `.exe` 发送 `uci` 探测：

- 回 `uciok` → 注册为 **UCI** 引擎；回 `ucciok` → 注册为 **UCCI** 引擎。
- 记录：引擎名（`id name`）、协议、作者、目录路径、**已缓存选项列表**。
- 无法识别为象棋引擎的 exe → 提示「无法识别为象棋引擎」，不注册、不崩溃、不中断扫描。

### 6.3 追加引擎三步法

1. 从 GitHub 等下载引擎压缩包，解压后把整个引擎文件夹放进 `engines\` 的子目录（或任意目录，用「添加外部引擎目录」）。
2. 确保 **exe 与权重文件在同一文件夹**（引擎自动加载同目录权重）。
3. 软件中点「重新扫描引擎」或重启 → 引擎出现在列表，选为己方/对手即可对战。

全程无需改代码、无需手写配置文件。详见 `docs\ENGINES.md`。

### 6.4 引擎管理面板

菜单「引擎 → 引擎管理…」（v1.5 起从工具栏移到这里）打开独立窗口，可以：列出全部已注册引擎（名称/协议/路径/可用状态）、重新扫描、添加外部引擎目录、打开引擎库目录、测试连接（发 `isready`）、设为己方引擎、设为对手引擎、移除（不删磁盘文件）。

## 八、胜率与概率公式（含来源与近似性）

### 8.1 胜率

```
winrate(cp) = 50 + 50 * ( 2/(1+exp(-K*cp)) - 1 )
            = 100 / (1 + exp(-K*cp))              （两式恒等）

K = 0.00368208      cp = 引擎分值（厘兵，1 兵 = 100 厘兵）
```

- `score cp` 以**走子方**为基准（UCI 约定）。本软件统一换算成红方胜率：黑方走子时对分值取负。
- `score mate N` 不走公式：N > 0 → 100%，N < 0 → 0%。
- **近似性说明**：中国象棋没有国际象棋那样的官方 WDL 统计模型，也没有公认的「厘兵 → 胜率」标定表。上式采用国际象棋引擎社区通行的 logistic 近似（K 值等价于每 100 厘兵约 ±9.6% 胜率）。象棋子力价值分布与国象不同，因此该胜率是**参考值，不是统计学意义上的真实胜率**。它单调、对称、过零点 50%，用于横向比较局面优劣是可靠的。

### 8.2 候选概率（温度 softmax）

```
p_i = exp(s_i / T) / Σ_j exp(s_j / T)
```

- `s_i` = 第 i 条候选的分值（`Score.Value()`），`T` = 温度（默认 120，可调 40~300）。
- T 越大分布越平坦，T 越小分布越尖锐（最优着法概率越大）。
- 实现中先减去最大分值以保证数值稳定：`exp((s_i - s_max)/T)`，结果完全等价。
- 将死候选折算为 ±200000 量级，因此在任意温度下概率都趋近 100%（这是符合直觉的：有杀就应当走杀）。
- 概率和恒为 100%（浮点误差 < 0.001%），界面上直接显示「概率合计」供核对。

## 九、坐标换算图（UCI ↔ 界面 ↔ 中文记谱）

### 9.1 棋盘坐标（与 UCI/UCCI 象棋协议完全一致）

```
rank 9   a9  b9  c9  d9  e9  f9  g9  h9  i9     ← 黑方底线（将 e9）
rank 8   a8  b8  c8  d8  e8  f8  g8  h8  i8     ← 黑方九宫
rank 7   a7  b7  c7  d7  e7  f7  g7  h7  i7     ← 黑炮 b7 / h7
rank 6   a6  b6  c6  d6  e6  f6  g6  h6  i6     ← 黑卒 a6 c6 e6 g6 i6
rank 5   ───────────── 楚 河 ─────────────
rank 4   ───────────── 汉 界 ─────────────
rank 3   a3  b3  c3  d3  e3  f3  g3  h3  i3     ← 红兵 a3 c3 e3 g3 i3
rank 2   a2  b2  c2  d2  e2  f2  g2  h2  i2     ← 红炮 b2 / h2
rank 1   a1  b1  c1  d1  e1  f1  g1  h1  i1     ← 红方九宫
rank 0   a0  b0  c0  d0  e0  f0  g0  h0  i0     ← 红方底线（帅 e0，a0 红方左车）
         a   b   c   d   e   f   g   h   i
```

- 红方在下（行 0 为红方底线），黑方在上（行 9 为黑方底线），**a0 是红方左车**，e0 红帅，e9 黑将。
- 内部线性索引：`Index = rank*9 + file`，取值 0~89。例：帅 e0 → 4；将 e9 → 85；黑车 i9 → 89。
- 屏幕绘制换算（只允许在 `ui/board.go` 里做）：
  `屏幕行 = 9 - rank`，`屏幕列 = file`。
- 着法格式固定 4 字符：`起点 + 终点`，如 `h2e2` = 炮二平五。

### 9.2 中文记谱规则（`notation` 包实现）

```
记谱 = [前/中/后] 棋子名 + 动作 + 目标
```

- **纵线号**：红方用汉字「一」~「九」，自红方右侧向左数 → `红方号 = 9 - file`；黑方用阿拉伯数字 1~9，自黑方右侧向左数 → `黑方号 = file + 1`。
- **动作**：`平`（同行走子）、`进`（向对方底线）、`退`（向自己底线）。
- **目标**：車/炮/兵/卒/帅/将用「移动步数」；馬/相/仕用「目标纵线号」。
- **同线同兵种多于一枚**时用 `前/后`（3 枚用 `前/中/后`，更多枚用 `前、二、三、…、后`）代替纵线号。
- **棋子写法**：红方用「帅仕相馬車炮兵」，黑方用「将士象马车炮卒」（红方「車/馬」用繁体，黑方「车/马」用简体）。

实例：

| UCI | 中文 | 说明 |
| --- | --- | --- |
| `h2e2` | 炮二平五 | 红炮 h2 → e2（9-7=2 → 二；9-4=5 → 五） |
| `b0c2` | 馬八进七 | 红馬 b0 → c2（9-1=8 → 八；9-2=7 → 七） |
| `h9g7` | 马8进7 | 黑馬 h9 → g7（7+1=8；6+1=7） |
| `b7b6` | 炮2进1 | 黑炮 b7 进一步（1+1=2） |

## 十、窗口、背景图与皮肤

### 10.1 系统窗口层

- 窗口标题：`象棋强软 v1.3.1`（标题与「关于」对话框共用 `version.VERSION` 常量）。
- 启动恢复上次窗口大小（`config.json` 的 `window_width` / `window_height`），关闭时自动保存。
- 紧凑布局：主题把 `SizeNamePadding` / `SizeNameInnerPadding` 调到 4，控件间距统一。
- 高分屏：Fyne 自动做 DPI 缩放；棋盘用 `canvas.Raster` 按**物理像素**光栅化（Fyne 传入的 `w,h` 已是设备像素），因此 150% / 200% 缩放下格线与文字不模糊、不裁切。
- 背景图为可选装饰层，不参与布局计算，不改变任何控件的可读性。

### 10.2 已知限制（Fyne 能力边界，如实记录）

| 限制 | 原因 | 本版处理 |
| --- | --- | --- |
| **不能设置窗口位置** | Fyne v2 的 `fyne.Window` 接口没有 `SetPos` / `SetPosition`（只有 `CenterOnScreen`），驱动层也未暴露 | 只恢复窗口大小；位置交给窗口管理器。`config.json` 仍保留 `window_x` / `window_y` 字段，供将来 Fyne 支持后启用 |
| **不支持无边框 / 圆角 / 阴影系统窗口** | Fyne 沿用操作系统原生窗口装饰，无 API 可关闭 | 本版沿用系统边框；棋盘与各面板内部有自绘的圆角与双线边框作为视觉补偿 |
| **不支持自定义窗口标题栏图标动画等** | 同上 | 仅设置窗口标题 |

### 10.3 背景图（二次元少女，护眼优先）

1. 程序从 `config.json` 的 `background_image` 读取路径，默认 `assets\background.jpg`（与 exe 同目录，相对路径按 exe 目录解析）。
2. 文件存在 → 作为整窗背景（`ImageFillStretch` + 平滑缩放），其上叠加半透明遮罩，遮罩不透明度由 `background_overlay` 控制（默认 65，范围 0~100），保证棋盘与文字可读性不下降。
3. 文件不存在 → **不报错**，回退为护眼纯色底（米黄 `#F6F0E2`），并在状态栏提示「未找到背景图 assets\background.jpg」。
4. 背景图由用户自行放置，程序**不下载任何图片**；换图只需替换文件或改 `config.json` 路径，无需改代码。

### 10.4 护眼配色

#### 五、可选字号档位（默认标准，想放大的人自己放大）

| 档位 | 倍率 | 实测按钮高度 | 说明 |
| --- | --- | --- | --- |
| **标准（默认）** | ×1.00 | 30.0px | 上表的密度即标准档 |
| 大 | ×1.22 | 34.0px | 用户自选 |
| 特大 | ×1.45 | 40.4px | 用户自选 |

三档都满足 WCAG 2.5.8（AA）的 24px 点击目标底线；三档严格递增（由测试守着）。
WCAG 2.5.5（AAA）的 44px 在本版**不作为默认要求**——用户明确要求密度优先。

菜单「设置 → 字号」三档带 ✓，点击**立即生效、不重启、不重建界面**。

实现（`ui/a11y.go`）：Fyne 的控件尺寸全部来自主题的 `Size()`，所以换档分两半：

1. **换主题**：按钮 / 菜单 / 输入框 / 列表行跟着重排；
2. **`ApplyFontScale` 走一遍界面对象树**：工程里写死字号的 `canvas.Text`
   （面板标题、状态栏、棋盘文字…）不归主题管，按「角色基准 × 新倍率」逐个换算；
   且只认「正好等于旧档位某个角色字号」的文字 —— 不会重复放大，也不会误改
   棋子文字这类跟着棋盘尺寸算的字号。

> ⚠ 更早一轮留下的坑（已修）：`SetFontScale()` 三个档位写好了，却**没有任何地方调用它**，
> 界面永远停在 ×1.00；而且就算调用了，只走主题也改不动写死字号的 `canvas.Text`。
> 现在 `Setup()` 在建控件**之前**设档位，换档另有 `ApplyFontScale` 兜住全部自定义文字。

#### 七、另外两处顺手修掉的真实缺陷

1. **界面上的空心方框（缺字形）**：实测本机字体渲染 `→ ← ↑ ↓ ·` 会显示成方框，
   而「关于」对话框、引擎列表、状态提示里正好都在用它们。
   已全部换成中文描述，并加了回归测试 `ui.TestNoMissingGlyphRunes`——
   它用 `go/parser` 扫全包字符串字面量，出现这些字符就直接测试失败（注释不管）。
2. **`config.json` 的 `version` 字段永远停在旧版本**：`Version` 只在 `Default()` 里赋值，
   `Load()` 又会被文件里的旧值覆盖，于是「一次性迁移」（线程/哈希/MultiPV 等于旧默认才换新默认）
   **每次启动都跑一遍**：用户手动把线程调回 16、哈希调回 4096 之后，下次启动会被悄悄改回去。
   现在 `Save()` 写入当前版本号，迁移只发生一次。

#### 九、菜单体检（v1.6.3，用户要求「所有菜单按键逐个检测」）

做法：加了验证钩子 `XQ_MENUSMOKE=1`（`ui/verify_hooks.go`）——启动后自动
**逐个调用菜单里的每一项**（跳过会拉起资源管理器/记事本的「打开目录」「使用说明」等），
每项之间停 400ms 并把弹窗收掉，任何一项 panic 都会带着「刚点的是哪一项」打到 stderr。
本轮实测：**30 个菜单项全部走通、零 panic**。

代码审查另外发现并修掉 3 个真实缺陷（都是「点了没反应 / 点了出别的事」这类）：

| # | 现象 | 真实根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 「设置 → 显示棋盘坐标 / 走棋音效」点完勾**不跟着变**，看着像没生效 | Fyne 菜单是静态的，勾选态只在 `buildMainMenu()` 时取一次；这两个开关改完没有重建菜单 | 两个 toggle 收尾调 `refreshMainMenu()` |
| 2 | 「对局 → 对局设置…」一点就**开始对战** | 它内部走 `SetMode("match")`，而 v1.6 加的「切到引擎对战就自动开赛」也在这条路径上 | 新增 `showMatchWithoutStarting()`：置 `matchNoAutoStart` 后只切界面不开赛 |
| 3 | 对战进行中点「局面 → 编辑局面」，摆了子下一着就被覆盖，像摆了没用 | 对战着法由 Runner 事件流驱动，与用户手改的显示局面互相打架 | 对战进行中拒绝进入编辑局面并给提示（同类软件在对局中也锁住局面编辑） |

顺带把「设置 → 棋盘：大/中/小」也加上了 ✓ 勾选态（按当前分栏比例判断，容差 1%）。

#### 十、v1.6.4：候选后续走法 + 对战可取消

**1）变招点开看后续走法**

每条变招现在可以点开，展开显示**这一招之后的引擎后续走法**（中文，最多 8 步），
**默认全部收起**（用户要求）。实现要点：

- 行内容包进 `tapArea`（新控件：任意内容 + 整块可点 + 悬停/选中的浅底反馈），
  因为变招行要按红黑分色，Fyne 的 `widget.Button` 做不到「一格一色」；
- 后续走法由 `a.pvChinese(l.PV, board, 8)` 逐条换算成中文，跟着候选一起下发
  （`SetCandidates` 多了 `pv []string` 参数）；
- 引擎本次没给后续走法时，点开也不展开空行（有测试守着）。

**2）对战可取消（照同类软件的做法）**

用户反馈「点引擎对弈后取消不了」。查同类软件：TCHESS 的「引擎执红 / 引擎执黑」
是 **toggle 按钮**，再点同一个按钮就停；象棋巫师同理（电脑执红/执黑 + 停止思考）。
本工程原来是「点模式按钮开赛、终止只能去菜单里找」，界面上根本没有停止入口。

改法：**工具栏「引擎对战」按钮变成开关**——开赛后按钮文案变成「**终止对战**」，
再点一次即终止（`App.ToggleMatch` / `refreshMatchButton`，状态变化时同步文案）。

#### 十五、多引擎同局面对比（Kibitzer）——**设计已定稿，开始实施**

1. 这个能力在同类产品里叫 **Kibitzer（旁观引擎）**，入口都在「引擎/窗口」菜单；**中文象棋软件没有等价功能**
   （象棋巫师的「副引擎」只用于引擎对战），做出来是差异化点；
2. 设置范式 = **每个引擎一套自己的参数（UCI 选项/线程/哈希/Multi-PV 行数）+ 一层可选的全局公共默认值
   （勾选即强制覆盖）**；而**时间语义是统一的**（「自由分析」无限时手动停 / 「同步每步时限」一个输入框管两个引擎），
   同类产品**没有**「每个引擎各填一套时制」的做法——我最初的设计正是这样，已按调研否掉；
3. 结果显示照 Arena：每引擎一张等高卡片（引擎名带底色 + 状态），排布支持堆叠 / 双列 / 合并视图；
   「两引擎首选着法不同时棋盘画双箭头 + 卡头分歧徽标」是同类都没做的差异点。

## 十一、棋盘绘制细节

- **抗锯齿矢量绘制**：棋盘底板用 `canvas.Raster` 按物理像素自行光栅化，所有图元（直线、圆、圆角矩形、圆弧）都按**像素覆盖率**做 alpha 合成，边缘平滑无锯齿。轴对齐线段走精确面积覆盖率，斜线（九宫）走距离场覆盖率。
- **外框**：圆角底板 + 粗外框 + 内侧细框（双线边框）+ 四角装饰方块 + 底板淡描边。
- **格线**：10 条横线贯通；9 条竖线中两侧边线（a、i）贯通，中间 7 条在河界处断开——与实体棋盘一致。
- **九宫斜线**：红黑两个九宫的 × 形斜线精确对齐交叉点。
- **河界**：「楚 河」「汉 界」分别居中于河界左右两侧。
- **兵/炮位标记**：红黑兵位与炮位绘制传统的小 L 形十字标记，棋盘边缘自动只画内侧的一半。
- **坐标标注**：四周标注（上下 a~i、左右 0~9），字号随棋盘缩放（有下限保证不糊）。
- **棋子**：`canvas.Circle` 实心 + 描边 + 右下偏移半透明阴影 + 汉字（红「車」黑「车」），大小随棋盘自适应（半径 = 0.435 格）。
- **交互反馈**：选中棋子金色方块高亮 + 加粗描边、合法落点绿色圆点、最近一步起点/终点双色高亮、鼠标悬停淡色高亮、**将军时被将一方将/帅所在格红色闪烁（420ms 周期）**、将死/困毙弹窗。

### 线程与并发约定

| 任务 | 运行位置 |
| --- | --- |
| Fyne 控件读写 | **只在主 goroutine**；后台一律通过 `fyne.Do(...)` 回到主线程 |
| 引擎进程读取 | 每个引擎一个独立 goroutine（`bufio.Scanner` 循环），路由 info / bestmove / 控制行 |
| 引擎思考 | 每次思考一个独立 goroutine，由「分析调度 goroutine」串行化 |
| 自动对战 | `match.Runner.Run` 一个 goroutine，通过容量 256 的事件 channel 推送界面 |
| 引擎扫描 | 独立 goroutine，逐个探测并把进度写回状态栏 |

**命令防重入**：`Client.Analyze` 用 `busy` 标志拒绝对同一引擎的并发思考；分析调度器在新请求到达时先 `cancel()` 旧请求并等它真正返回（确保 `stop` + `bestmove` 已经处理完）才发起下一次。

**超时与崩溃恢复**：`Analyze` 有硬超时（限时模式 = 标称限时 + 60 秒；深度模式 = 60 秒 + 每层 3 秒）；超时先发 `stop` 再等 3 秒；进程退出通过 `exited` channel 感知并给出带 stderr 尾部的错误。程序退出时对全部引擎发 `quit`，2 秒未退出则强杀。

### 14.3 性能实测明细

**桥接模式连续 50 次「粘贴着法序列 + 一键复制最佳着法」**：

```
压力测试：连续 50 次「粘贴着法序列 + 复制最佳着法」总用时 257ms，单次最慢 8ms（平均 5.133ms）
```

- 这 50 次全部在主 goroutine 上同步执行（与用户真实操作完全一致），因此 **8 ms 就是界面可能被阻塞的最长时长**，远低于人眼可感知的阈值。
- 优化前该数字是 12.357 s / 单次最慢 758 ms。瓶颈是棋盘每次重绘要对 32 枚棋子 + 38 个坐标 + 2 个河界字调用 72 次 `fyne.MeasureText`（每次都要解析字体、整形字形）。加入进程内文本测量缓存后降到 257 ms（**约 48 倍提升**）。
- 曲线位图也做了「尺寸 + 数据版本」双键缓存，数据没变时不再重新光栅化。

**引擎搜索性能**（Pikafish 2026-09-06，16 线程，1024MB 哈希）：约 **171 万 nps**，3 秒可达约 **514 万节点**、深度 14~16（MultiPV=8 时）。对战报告中的平均 NPS 为 178~182 万。

### 14.5 本次开发中实际修掉的问题（如实记录）

| 问题 | 现象 | 修复 |
| --- | --- | --- |
| 下拉框无限递归 | 程序启动后卡死、窗口不显示（进程活着但无窗口） | `Select.SetSelected` 触发 `OnChanged` → 又回头调用 `syncEngineSelects`。改为「静默设置选中项」+ 重入标志 |
| 参数被覆盖成滑块最小值 | 参数面板显示 MultiPV=1、温度 T=40、限时 0.1 秒 | `SetValues` 初始化时第一个滑块赋值就触发 `OnChanged`，而其余滑块还在最小值上。加入 `suppress` 标志屏蔽初始化期回调 |
| 窗口大于屏幕 | 1920×1080 @130% 缩放下，1500 逻辑单位 = 1950 物理像素，右侧与底部被裁掉 | `Canvas().Scale()` 在窗口真正显示前仍是 1.0，一次校正不够。改为显示后连续 8 轮收敛校正（`ui/screen_windows.go` + `App.clampWindow`） |
| 文本测量无限递归 | 启动即 `fatal error: stack overflow`（压力测试时暴露） | 批量替换误把 `measureTextCached` 内部的 `fyne.MeasureText` 也替换成了自身。已修正为调用原函数 |
| 首次运行不生成 config.json | 需求要求「不存在则默认创建」，实际要等 20 秒周期保存 | `Setup` 末尾判断文件不存在则立即保存 |
